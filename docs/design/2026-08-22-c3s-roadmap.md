# c3s roadmap — safety, correctness, speed, then k9s parity

**Date:** 2026-08-22
**Status:** approved, Phase 0 in progress
**Baseline:** 53 files, 24,853 LOC, 381 tests, 3.4 MB ReleaseFast binary, Zig 0.16.0

## Goal

Make c3s a daily-driver replacement for k9s. Faster, and honest about what it does.

## Non-goals (explicitly out of scope)

Decided by the repo owner: **XRay, Pulses, Popeye, HTTP benchmarks, and the plugin
system.** These are k9s subsystems rather than daily-driver features; Popeye alone is a
separate upstream project with ~100 checks. Not deferred-and-maybe — out.

## Why parity comes last

The original request was "re-check the design, make it faster and better, and copy the
needed k9s functions". Two parallel audits (feature-gap and design/performance) changed
the shape of that request, and this ordering is the result.

c3s's problem is not primarily missing features. It has **safety defects in shipped
behaviour** and **a UI that advertises capabilities it does not have**. Every feature on
the daily-driver list is a *mutation* — exec, delete, scale, restart, cordon, drain,
edit. Adding mutations on top of a non-functional read-only guard and a delete that can
target the wrong cluster multiplies blast radius instead of adding value.

So: safety, then correctness, then cheap speed, then structure, then features.

## Verified findings

Everything below was confirmed by reading the code, not taken from a report. Findings
that could not be confirmed are marked as such and excluded from phase scope.

### Safety (Phase 0)

**S1. `--readonly` is inert.** `cli.zig:76` sets it, `cli.zig:155` documents it in
`--help`, two tests assert the parse — and it is referenced **zero** times outside
`cli.zig`. Meanwhile delete is live: `App.zig:1424` and `App.zig:1531` both call
`deleteResource`, with a force variant labelled "Kill" (`App.zig:1515`). A user running
`c3s --readonly` against production believes mutations are blocked. They are not.

**S2. Delete can target the wrong cluster.** `K8sService.zig:1619` hand-builds
`{"kubectl","delete",…}` with no `--context`. `buildKubectlArgv`'s own doc comment
(`:750-757`) exists to prevent exactly this: *"after an in-app context switch, kubectl's
own current-context may point at a DIFFERENT cluster"*. Every other kubectl invocation
in the file routes through it; the one destructive call does not. The correctly computed
`path` at `:1609-1613` is allocated and freed unused in that branch, which suggests the
kubectl path was bolted on separately.

**S3. Permissions matrix reports "denied" when it never asked.** `checkAccess`
(`K8sService.zig:1666`) has no `use_kubectl` branch, while its immediate neighbours
`getRawJson` (`:1602`) and `getPodLogs` (`:1647`) both do. On any cluster where direct
TLS failed and `verifyOrFallback` selected the kubectl transport — the standard
EKS/TLS-interception path this codebase explicitly handles — all 48 calls fail and
`auth_access_tab.zig:111-113` swallows each with `catch { continue; }`. Every cell
renders as denied. Same gap in `listRBACPolicies`, `detectCedarAuth`,
`getAuthorizationConditions`. A security view that says "you have no access" when it
failed to ask is worse than showing an error.

**S4. The help screen advertises what does not exist.** `cordon` (5 mentions) and
`drain` (4) appear in `keybindings_data.zig`/`keybindings_vm.zig` with zero
implementation; the help also lists 11 views that do not exist. `tasks/lessons.md`
already records the rule: *"Hints/help must not advertise unimplemented actions."*

This one also has a second-order cost worth stating: **any feature estimate built by
grepping for names will read as near-parity.** It is not. Future planning must check
dispatch, not help text.

### Correctness (Phase 1)

- **C1.** `TableState.clearItems` (`:95-106`) clears `items` but not `filtered_indices`,
  `selected_row` or `scroll_offset`; `getSelectedItem` (`:287-292`) bounds-checks
  `selected_row` against `filtered_indices` but never the resulting index against
  `items`. Reachable without OOM via `AuthorizationView` refresh-while-unreachable.
- **C2.** Startup panic: `config.zig:97-98` strips quotes with
  `theme_name[0]=='"' and theme_name[len-1]=='"'` — for `len == 1` both indices are the
  same byte, so `[1..0]` panics. A config line `theme: "` kills launch, not behind a
  `catch`. Same function does substring matching, so `# theme: x` in a comment parses as
  live config.
- **C3.** Filter text borrows the command-input buffer without duping —
  `ContextsView.zig:105`, `LogsView.zig:77` — and `hide()` calls
  `clearRetainingCapacity()` immediately after. `TableState.applyFilter` (`:257-261`)
  dupes-before-free *with a comment explaining why*; these two hand-rolled it and
  dropped that.
- **C4.** Free-then-fallible-realloc at six sites (`TableState.zig:113,118`,
  `HelpView.zig:43-51`, `resource_view.zig:362,190`, `auth_condition_tab.zig:58`).
- **C5.** Unguarded `.object` on unvalidated `json.Value` at ~8 sites; the guarded style
  is used elsewhere in the same file, so this is inconsistency rather than ignorance.
- **C6.** `:` `?` and `G` cannot be typed into the filter or command palette.
  `Terminal.readKey` (`:361-363`) converts them to distinct Key variants, but the
  command-input branch (`App.zig:822-826`) accepts only `.char` in 32..126. Filtering
  for a pod named `Gateway` is impossible. Corollary: `App.zig:887` and `:890-904` are
  unreachable dead arms duplicating the live `.colon`/`.question_mark` handlers.
- **C7.** `getPodLogs` sends no `container=` parameter, so logs 400 for any
  multi-container pod (Istio sidecars, init-heavy workloads).

- **C8.** `resource_configs.zig:1239` defines an `endpoints` view and `:1266` a
  `storageclasses` view, but `ResourceType` (`k8s_types.zig:18-44`) has neither member.
  `stringToEnum` therefore returns null and describe / yaml / delete are dead in both
  views, which otherwise look functional. Verified.
  (The audit also flagged `ResourceType.contexts` mapping to `/api/v1/contexts`; that
  one is annotated `// not a real K8s resource` in the source, so it is deliberate, not
  a defect. Excluded.)

### Phase 0 outcome (2026-08-22)

S1–S4 done. Two findings surfaced while fixing them, both recorded above as they were
discovered rather than assumed:

- `deletePod` had never compiled. Adding the readonly guard made Zig analyse it for the
  first time; it called `pods_client.delete(...)` with the wrong receiver and arity.
  Nothing had ever referenced it.
- The real cause of the all-denied permissions grid was not only the missing transport
  branch: `AccessStatus` had no "unknown" state and every field of `AccessRow`
  **defaulted to `.denied`**, so any failed check rendered as a confident denial. Fixed
  by adding `.unknown` (rendered `?`, dimmed rather than red) and defaulting to it.
- A test in `keybindings_vm.zig` asserted that cordon and drain WERE advertised, so the
  suite actively enforced the lie. It is now inverted into a tripwire.

### Performance (Phase 2)

Measured on the shipped binary by counting the ANSI stream; frames are exactly countable
because DEC-2026 sync-end delimits them.

| Metric | 200×50 |
|---|---|
| Bytes per frame | 44,872 |
| SGR color sequences | 2,906 (25,259 B — 56%) |
| Visible payload | 12,126 B (27%) |
| RSS at idle | 3.7 MB |

- **P1. Borders are 67% of the frame.** `box_drawing.zig:74-78` writes each border glyph
  via `writeStringWithTheme` — setCursor(9) + fg(17) + bg(5) + glyph(3) + reset(4) = 38
  bytes per character, 792 glyphs per frame. The cursor is already in position and the
  colors never change. One run per line: 30,096 → 2,516 bytes, **−61% total frame
  bytes** from ~6 lines of code.
- **P2. Up to 100 ms input lag.** `renderIfNeeded` correctly drops a frame and leaves
  `dirty = true`, then the loop blocks in `poll(…, 100)`. Fix: poll for
  `min_frame_time − elapsed` when a frame was dropped.
- **P3. 6 malloc/free per frame** in `Header.updateClusterInfo` (`:441-449`), called
  unconditionally every frame. The next function down already short-circuits on
  `mem.eql` — the pattern was known and not applied.
- **P4. All 35 skins lose their row-cursor colors.** `theme_loader.zig:186` breaks when
  `found_count >= countUniqueKeys()` = 14, but `theme_mappings` has **17** entries
  (verified) because three yaml keys each fill two mappings. `title_highlight`,
  `selected_fg` and `selected_bg` are never reached, so the selected-row highlight falls
  back to hardcoded defaults in every skin. The existing test asserts only
  `main_fg.len > 0`, which is why it never caught this.
- **P5. −145 KB binary (5%)** from two mechanical fixes: `sortBy` takes a *comptime*
  getter, so Zig emits one full `sort.pdq` per (view, column) pair — 130 KB for a sort.
  `setConnectionError` takes a comptime string, monomorphizing per view for a concat.

### Architecture (Phase 3)

- **A1. Back buffer + per-row diff in `Terminal`.** There is no damage tracking; moving
  the cursor one row repaints everything, and each cell is painted 2–3× per frame
  (box interior fill, selection bar, then text — 9,118 spaces measured into a
  10,000-cell screen showing a small dialog). This is the only fix that scales with
  terminal size instead of fighting it: a cursor move goes from ~45 KB to a few hundred
  bytes.
- **A2. Split `K8sService.zig` (2129)** — but delete first: the `listAllGeneric` family
  `@memcpy`s structs containing `json.Value` out of a `Parsed` then deinits it (the
  use-after-free already recorded in `tasks/lessons.md`), and ~46 wrappers built on it
  have zero production callers. Then `Transport`, `Connection`, `Authorization`,
  `Resources` — the last with a `ListOptions` parameter from day one, since its absence
  is why there are no selectors and no pagination anywhere despite klient supporting
  both.
- **A3. Split `App.zig` (1833)** into Loop / Compositor / ViewRegistry / KeyRouter /
  Exec / Prompts. Ten key-handler arms are byte-identical 8-line copies.
- **A4. `AuthorizationView.zig` (1817) is 71% tests** (first test at line 530, verified),
  and `:1300-1817` is a weaker duplicate of the block above it — `DebugAllocator` that
  prints leaks without failing, versus `testing.allocator` in the original. Deleting it
  restores leak detection as a gate.
- **A5. Erase the view type.** `ResourceView(...)` yields a distinct type per resource,
  so `App` cannot hold views in an array: 37 typed pointer fields, a 30-field anonymous
  struct, the assignment block, `deinit`, and a switch per command. `ViewManager` stores
  `View` as two parallel `ArrayList(usize)` of `@intFromPtr`, which launders pointer
  provenance and can desync.
- **A6. Three sources of truth for the keymap** (~1,160 LOC), none authoritative:
  `hints.zig`, `keybindings_data.zig` + `keybindings.zig`, and the actual dispatch. Every
  drift instance in C6/S4 traces here.

### Correction: the test-all drift was mostly NOT caused by zig-klient (2026-08-22)

Phase 1's commit message said the three stale test calls "drifted when the klient
migration" changed those signatures. **Three of the four drifts were c3s-internal.**
Verified with `git log -S`:

- `deleteResource` gaining `force` and `getPodLogs` gaining `previous` — both are c3s's
  OWN `K8sService` methods (they do not exist in zig-klient at all), and both params
  were added in c3s commit `be95cba`.
- `listNamespaces` returning `ParsedList` — `ParsedList` is defined in c3s's own
  `K8sService.zig`, not in klient.
- Only `tls.validateCertKeyPair` was genuinely a klient deletion (klient 0.4.0 dropped
  the mTLS-only helpers).

The lesson is stronger with the right attribution, not weaker: an uncompiled test file
drifts from **its own codebase**, not merely from its dependencies. Blaming the
dependency made it sound like an integration problem that a version pin would catch. It
was not — c3s changed its own signatures and nothing noticed, because `test-all` was not
running. Which is exactly why it now runs in CI.

### A1 (back buffer) deferred deliberately — not skipped

The spec calls A1 the largest payoff and says it should land alone. On inspection it is
also not a contained change: a cell-based back buffer requires callers to write CELLS,
but every call site writes pre-formatted ANSI strings (colour + text). Converting them
reaches across the whole of `src/view/`, and the spec's own risk note says this is the
one change that could regress rendering broadly.

It is therefore left for a dedicated session rather than attempted in the middle of a
batch. Two related items were re-examined and one shrank:

- "Skip createBox's interior fill" is NOT the easy win it looked like. `fillRow` is
  already chunked and writes its colours once, so the interior costs about a byte per
  cell, not the ~38 that per-character *styling* cost. And skipping the fill is only
  safe where a view repaints every row including empty ones, which varies per view;
  getting it wrong leaves stale glyphs on screen. Needs per-view verification, not a
  blanket change.
- The remaining measurable win in the render path is the per-row diff, which is part of
  A1 proper.

### Correction to A4 (2026-08-22)

The audit claimed `AuthorizationView.zig:1300-1817` is "a verbatim duplicate of the
test block above it, pair-for-pair" and that deleting 518 lines was safe. **That is
wrong.** The earlier block has 30 tests, the later has 17, and they share **zero** test
names. Deleting them would have removed 17 real tests. Checked before acting; the
"delete ~518 lines" item is withdrawn.

The second half of that finding was correct: 14 tests used a `DebugAllocator` and
*printed* leaks to stderr without failing. A leak check that cannot fail is not a
check, so those now use `std.testing.allocator`. All 14 pass, meaning the code was
already leak-free and only the check was decorative. Verified the gate is real by
injecting a deliberate leak and confirming the suite fails.

Lesson for the remaining phases: this audit is a good lead generator and an unreliable
authority. Every claim gets checked before it is acted on — this one would have cost
17 tests.

### Data path (Phase 3, lower priority)

Better than expected: no K8s call per frame or per keystroke, resource views are free of
N+1, metrics are one aggregate call. Real issues are **peak** memory and **staleness**:

- No `limit`/`continue` anywhere, and kubectl mode simultaneously holds a 128 MB-capped
  subprocess body, a `.alloc_always` Parsed arena, and the row strings. A large-cluster
  `GET /pods` is the one place the 50–100 MB target is at risk.
- ConfigMaps and Secrets download full payloads to display a key count, defaulting to
  all namespaces. Full base64 secret material transits a curl pipe for an integer.
- **Namespace switch invalidates nothing** — you see the old namespace's pods under the
  new namespace's title. Context switch is handled correctly; the namespace path never
  got the same treatment.
- No auto-refresh exists; `--refresh` is parsed, unit-tested, and read nowhere, while
  `--help` advertises a 2-second default. Header CPU/MEM is fetched once at startup and
  is *fabricated* anyway ("assume ~4 cores and ~16GB per node").
- The authorization tab is a genuine N+1: 8 resources × 6 verbs = 48 sequential
  `SelfSubjectAccessReview` POSTs per refresh. One `SelfSubjectRulesReview` replaces all.

## Phases

Each phase is independently shippable and verified before the next begins.

### Phase 0 — safety and truth
S1 readonly guard (enforced at the single mutation chokepoint, not per-call-site),
S2 route delete through `buildKubectlArgv`, S3 add the `use_kubectl` branch to the four
authorization methods, S4 stop advertising unimplemented keys.
**Verification:** a test asserting readonly blocks every mutation entry point; a test
asserting the delete argv contains `--context`; every advertised key resolves to a live
handler.

### Phase 1 — correctness
C1–C7. **Verification:** a regression test per defect, each one demonstrated to fail
before the fix (mutation-tested, per the standing rule that a test asserting its own
inputs proves nothing).

### Phase 2 — speed, cheap
P1–P5. **Verification:** re-measure bytes/frame against the 44,872 baseline; re-measure
binary size against 3.4 MB; confirm the skin fix changes rendered cursor colors.

### Phase 3 — structure
A1–A6 plus the data-path items. Largest payoff is A1. **Verification:** bytes/frame for a
cursor move; tests stay green; no behaviour change intended.

### Phase 4 rescoped after verification (2026-08-22)

Checked what actually exists before planning any of it, and Phase 4 is much smaller
than the gap analysis implied.

**Already implemented, and reachable from keys:** exec/shell (`kubectl exec -it ... --
sh -c "bash || sh"`), attach (`kubectl attach -it`) and edit via `$EDITOR`
(`kubectl edit`) — all in `App.runInteractive`, wired at the `.request_edit` /
`.request_shell` / `.request_attach` arms. c3s does **not** use klient's WebSocket
exec/attach/port-forward at all, which conveniently sidesteps klient's Zig-0.16
`TlsInitializationFailed` limitation: those APIs all need a `*WebSocketClient`, so they
would not have worked anyway.

`runInteractive` also already injects `--context`, with a comment describing the
wrong-cluster hazard. I suspected a repeat of the Phase 0 delete bug and was wrong.

**A real hole in the Phase 0 guard, found here.** `runInteractive` spawns kubectl
directly and therefore bypasses `K8sService` completely, so the service-level
`--readonly` guard never saw it: `c3s --readonly` still permitted `kubectl edit`. Now
gated at those three call sites. shell and attach are gated too — an interactive shell
can do anything the container can, so read-only has to be a promise about the cluster
rather than about which API verbs this process happens to call.

The general lesson, which is worth more than the fix: **a guard at one layer is not a
guard.** The Phase 0 commit claimed the service boundary was the right place "so a new
caller cannot forget it" — true for callers that go through the service, and this one
does not.

**Still genuinely missing** (to be re-verified individually before estimating, given
this audit's record): port-forward, scale/restart/cordon/drain, log controls (follow,
previous, timestamps, since, wrap), decode secrets, YAML-view filter and fullscreen,
custom columns via `views.yaml`, auto-refresh (`--refresh` is parsed and read nowhere),
live filter, and the `endpoints`/`storageclasses` `ResourceType` members (C8).

### Phase 4 — k9s daily-driver parity
exec/shell, port-forward, edit via `$EDITOR`, scale/restart/cordon/drain, log controls
(follow, previous, timestamps, since, wrap), decode secrets, YAML-view filter and
fullscreen, custom columns via `views.yaml`, auto-refresh, live filter.
zig-klient already provides exec/attach/port-forward over WebSocket and logs, so most of
this is wiring rather than new protocol work — to be confirmed per feature before
estimating.

## Risks

- **Phase 3 A1 is the one change that could regress rendering broadly.** It should land
  alone, behind its own verification, not bundled with features.
- The keymap has three sources of truth; changing keys during Phase 4 without fixing A6
  first will reintroduce drift.
- `docs/superpowers/` is gitignored in this repo, so specs live in `docs/design/`.

### Phase 4 progress and per-feature verification (2026-08-22)

Landed: auto-refresh (#7), live filter (#8), log follow/previous controls (#9), node
cordon/uncordon (#10). Each was verified individually before implementation, as this
section's own warning demanded — and in three cases the verification changed the work.

**Cordon/uncordon: kubectl on both transports, deliberately.** `scaleDeployment` and
`setCronJobSuspend` reach straight for `self.client.?` with no `use_kubectl` branch —
the same defect class already fixed in `checkAccess`, which fails under the
kubectl-proxy transport. They are currently dead code (zero App callers), so the bug is
latent rather than live, but any Phase 4 work that wires them up must fix that first.
New mutations route through `buildKubectlArgv`, which also pins `--context`.

**Drain is not bound, and that is a standing constraint rather than an omission.** k9s
puts drain on `r`, which in c3s is refresh; binding a workload-evicting operation to the
key users press to refresh is an accident generator. It also evicts running pods, so it
needs the confirmation flow delete has. Cordon needs neither — it is reversible and
evicts nothing, only stopping *new* pods from being scheduled. Whoever implements drain
must choose a different key and add confirmation.

**The Phase 0 "help advertises actions that do not exist" defect is a recurring class,
not a one-off.** Three instances found so far:

1. Nodes view advertised Cordon/Uncordon/Drain with no implementation anywhere.
   Cordon/uncordon are now real; the drain hint stays removed.
2. Pods view advertised `c` = "Copy" with no implementation anywhere in the codebase.
   Found incidentally while checking whether `c` collided with anything. Hint removed.
3. A `portforwards` `ViewType` existed with "start"/"stop" bindings **and a test
   asserting they exist** — but there was no port-forwards view and nothing could
   navigate to one. Closed: `:pf` now exists, Ctrl-D stops a forward, and the bindings
   test is honest without needing to change.
4. `cli.zig` advertised ten config paths on the splash screen; seven had no reader
   anywhere. Fixed, with an `unread_path_labels` tripwire.

The countermeasure that works is the **inverted tripwire**: assert the binding does NOT
exist, so the suite fails if someone re-advertises an unimplemented action, then flip it
to a positive assertion in the same commit that implements the action. Note instance 3
shows a test can just as easily enforce the lie as catch it.

**Port-forward is half-built.** Spawning works end to end (`F` -> prompt -> `kubectl
port-forward` via `spawnKubectl`, tracked in `App.port_forwards`). What is missing is the
list view: forwards are fire-and-forget, with no way to see or stop one, and a dead
forward's entry lingers. That is the k9s `:pf` feature and it is what makes instance 3
above true.

**Bad mutants are a real failure mode.** Verifying the drain tripwire, the first mutation
injected the binding into the *pods* set rather than `loadNodesBindings`, so the
nodes-only tripwire correctly did not fire — indistinguishable at a glance from a
surviving mutant. When a mutant survives, confirm the mutation landed where intended
before concluding the test is weak.
